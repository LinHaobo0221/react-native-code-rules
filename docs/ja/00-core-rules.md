# React Native / Expo Codex 実行ルール

> 本書は、リポジトリのルートにある `AGENTS.md` で必読と定められたコア実行ルールである。React Native / Expo コードの生成、変更、リファクタリング、レビューの前に、毎回全文を読まなければならない。詳細な説明と、プラットフォーム、Figma、パフォーマンス、テスト、セキュリティの要件は、同じディレクトリの[開発規約の索引](README.md)を参照する。

## 1. 6 つの厳守ルール

1. **作る前に調べる**：コンポーネント、Hook、ユーティリティ、フローを追加する前に、現在の feature、`shared`、トークン、公開エントリーポイント、同じユーザーの意図を表す実装を検索する。
2. **同じ理由で変わる場合だけ抽出する**：意味、状態に関する契約、将来の変更理由が一致する場合だけ共通化する。見た目が似ているだけでは十分ではない。
3. **安定して再利用できる最も低い層を選ぶ**：トークン、primitive、純粋関数、Headless Hook、Feature Pattern、Shared Pattern の順に検討し、いきなり万能コンポーネントを作らない。
4. **Feature First**：安定していない抽象化は feature 内に留める。複数の feature で使われ、特定の業務に偏らず、契約が安定してから `shared` に移す。
5. **1 つのアクションに 1 つの統括箇所**：主要なユーザーアクションごとに、処理全体を統括する唯一の箇所を設け、重要な手順をそこで順を追って読めるようにする。
6. **処理を渡すだけの関数を禁止する**：変換、検証、不変条件、分岐、エラーマッピング、並行制御、副作用の境界、実装の差し替えやすさのいずれも加えないラッパー関数は削除しなければならない。

## 2. コーディング開始前に必ず出力する内容

```text
対象ファイル：
- path：責務

再利用の検討：
- 候補コンポーネント / Hook / Token：
- 判断：そのまま再利用 / 拡張 / 低い層の機能を抽出 / 独立した実装を維持
- 理由：意味、状態に関する契約、変更理由

主要アクションの経路：
UI callback
-> Controller action または直接の handler
-> 必要に応じて Use Case
-> API / storage / cache adapter
-> typed result
-> UI state / navigation / feedback

パターンの選択：
- 使用するパターンと、それが解決する実際の複雑さ
- 導入する必要のないパターンを明示
```

再利用候補が見つからない場合は、「検索済み。意味が一致する実装は見つからなかった」と記載する。

## 3. UI 共通化の判断

### 3.1 重複の種類と適切な配置先

| 重複する内容 | 優先する抽象化 |
| --- | --- |
| 色、間隔、角丸、フォント、モーション | トークン |
| UI 構造も操作の意味も同じ | feature UI。安定後に shared UI |
| 同じ振る舞い、異なる UI | Headless Hook / 純粋な状態モデル |
| 同じバリデーション、変換、セレクター | `model/` または純粋関数を置く `utils/` |
| 同じ多段階の業務処理 | `use-cases/` |
| プラットフォーム、サードパーティ SDK、DTO の差異 | Adapter |
| 現時点の見た目だけが似ている | 独立した実装を維持し、低い層の primitive を再利用 |

判断のポイント：

> 要件が変わったとき、これらの箇所は同じ理由で一緒に変更されるべきか？

### 3.2 Shared UI がすべて満たさなければならない条件

- feature 名に依存せず、中立的な名前で表現できる。
- 利用側で、状態、操作、アクセシビリティ、プラットフォームに関する契約が一致する。
- 同じ理由で変更される見込みがある。
- ルート、API、認証、ストレージ、Use Case、feature のストアを import しない。
- Props にページ名、ルート、feature の列挙型、特定の利用側専用の真偽値を含めない。
- 内部スタイルを大量に上書きしたり、`mode="custom"` を使ったりしなければ再利用できない設計にしない。

### 3.3 抽象化のタイミング

- 1 回目：feature 内で完結する、わかりやすい実装にする。
- 2 回目：意味と変更理由を検討する。低い層の機能だけを抽出してもよい。
- 3 回目も安定して使える場合：通常は共通部分を抽出し、既存の実装を移行する。
- プロジェクトのデザインシステムの primitive と、セキュリティ上の不変条件は、より早く抽出してもよい。

### 3.4 コンポーネント API

- 選択肢が限られる見た目の違い：`variant`、`size`、`tone`。
- 実際に構造が異なる場合：コンポーネントの組み合わせ、children、slot。
- 状態は業務層で制御する：外部から制御する props + `onXxx`。
- 大量の真偽値、巨大な設定、ルート判定、スタイルを無制限に上書きできる仕組みを使わない。
- 共通化後はすべての利用側を更新し、重複する旧版を削除する。

## 4. ロジックと制御フロー

推奨経路：

```text
Page
├── View / feature UI -> shared UI
└── Controller Hook
    ├── optional Use Case
    ├── Reducer / Model
    └── API / Adapter
```

### 4.1 単純なフロー

少量の局所的な状態、1 回の同期アクション、業務ルールを伴わない 1 回の API 呼び出しといった単純な処理には、ハンドラーに直接処理を書いてよい。形式を整えるために Use Case、Repository、Factory、クラスを作らない。

### 4.2 複雑なフロー

1 つのユーザーアクションに、バリデーション、複数の副作用、キャッシュの整合性、送信ロック、キャンセル、リトライ、冪等性、複数の呼び出し元への対応のいずれかが含まれる場合は、次を使用する。

- Controller：React のライフサイクル、UI の状態、アクションの受付、ナビゲーション、フィードバック。
- Use Case：React に依存しない業務処理、その実行順序、型を持つ結果。
- Reducer / 状態機械：互いに排他的な状態、不正な組み合わせ、明示的な状態遷移。
- Adapter：プラットフォーム、ネイティブモジュール、サードパーティ SDK、DTO の差異。
- Strategy：同じアルゴリズムに複数の実装が実際に存在する場合。
- Repository：複数のデータソースや、キャッシュ／オフラインの方針を統一する必要がある場合。

### 4.3 禁止する呼び出しチェーン

禁止：

```ts
const handleSave = () => submit();
const submit = () => executeSave();
const executeSave = () => service.save(form);
```

関数を残してよいのは、少なくとも次のいずれかの役割を担う場合だけとする。

- 入力または出力の変換
- バリデーション／不変条件の保証
- 分岐と順序の決定
- エラーマッピング
- 副作用の境界を設ける
- キャンセル／ロック／冪等性の保証
- 差し替え可能な実装
- 必要な計測処理

Controller のアクションは、処理全体を統括する唯一の箇所を直接呼び出す。同じページ内で直接表現できるフローを EventBus、Context、モジュール単位のシングルトンで隠さない。

### 4.4 Use Case の制約

- ユーザーの意図に沿って命名する：`publishPost`、`updateProfile`。
- React、React Native UI、Expo Router、Toast、ページコンポーネントを import しない。
- 判別可能なユニオン型（discriminated union）、または型を持つ結果を返す。
- 1 行の API 呼び出しのために空の Use Case を作らない。
- 関数ごとに意味のないインターフェースやクラスを作らない。

### 4.5 Reducer の制約

- Reducer は純粋な状態遷移だけを行う。
- リクエスト、ナビゲーション、ストレージ、Toast は Controller / Use Case が実行する。
- 判別可能なユニオン型で、真偽値の不正な組み合わせを防ぐ。
- サードパーティの状態機械ライブラリの導入を強制しない。

## 5. ディレクトリと依存関係

```text
app -> feature pages
feature pages -> feature ui -> shared/ui
feature pages -> hooks/controllers
hooks/controllers -> use-cases / model / api / shared
use-cases -> model / api / shared
api -> shared/api
```

- `shared` は `features` を import しない。
- UI はルート、API、認証、ストレージ、Use Case を import しない。
- Model は React、Router、API を import しない。
- Use Case は UI、Router、Toast を import しない。
- API は Page/UI を import しない。
- 無制限の `export *` で feature の内部実装を公開しない。
- 責務が明確でない `helpers.ts`、`common.ts`、`manager.ts`、`service.ts` を作らない。

## 6. 完了前の必須チェック

- [ ] 既存のコンポーネント、Hook、トークン、ルール、フローを検索した。
- [ ] 意味、状態に関する契約、変更理由が一致することを根拠に共通化している。
- [ ] 抽象化が、安定して再利用できる最も低い層にあり、万能コンポーネントがない。
- [ ] Shared props に特定の利用側専用の例外処理がない。
- [ ] 置き換えられた重複実装を削除し、直接の利用側を確認した。
- [ ] 主要なアクションごとに、処理全体を統括する唯一の箇所がある。
- [ ] `handle -> do -> execute -> service` のように処理を渡すだけの呼び出しチェーンがない。
- [ ] Use Case、Reducer、Strategy、Adapter、Repository のすべてに実際の導入理由がある。
- [ ] Use Case に UI/Router がなく、Reducer に副作用がない。
- [ ] 関連する Shared UI、Controller、Use Case、Reducer をリスクに応じてテストした。
- [ ] 最終説明に、再利用の判断、アクションの経路、パターンを選んだ理由、検証結果、残る差異を記載した。
