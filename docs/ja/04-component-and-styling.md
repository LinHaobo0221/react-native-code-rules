# 4. Page、UI、再利用、Controller、スタイルのルール

### 4.1 Page の責務

Page が担当する内容：

- ページ構造とセクションの組み立て
- ページまたはフローの Controller Hook の呼び出し
- UI コンポーネントへの状態と、ユーザーの意図を表すアクションの受け渡し
- ページ単位での読み込み中、エラー、データなし、コンテンツ表示の切り替え
- Controller が公開する状態とアクションの接続。ページ自体で Use Case の内部的な結果を解釈しない

推奨するページの記述形式：

```ts
const { state, actions } = useProfileEditorController();

return (
  <ProfileEditorView
    value={state.form}
    status={state.status}
    onChange={actions.changeField}
    onSubmit={actions.submit}
  />
);
```

Page に抱えたままにすべきでないもの：

- 大量の入力状態と、互いに呼び出し合うハンドラー
- API、キャッシュ、ストレージにまたがる複雑な処理の統括
- SVG、グラデーション、装飾の細かな実装
- 互いに無関係な複数のセクションの JSX 全体
- 大量のハードコードされたデータ

単純で、そのページ内で完結し、共通化する価値のない処理には、少量の `useState` と 1 つのわかりやすいハンドラーを直接使ってよい。形式を整えるために Controller や Use Case を作る必要はない。

### 4.2 Feature UI の責務

Feature UI は現在の機能内の表示とユーザー入力を担当し、props から状態とコールバックを受け取る。

原則として担当しない内容：

- ナビゲーションの判断
- API リクエスト
- 認証またはストレージへのアクセス
- 複数のページで共有する業務の正規データ
- ページのライフサイクルに強く依存する副作用
- Use Case の呼び出し、または複数の業務アクションの実行順序の組み直し

UI コールバックは、`onSubmit`、`onRetry`、`onSelectPlan` のようにユーザーの意図を表すものとする。`onCallUpdateEndpoint` のように内部の実装を表す名前にはしない。

### 4.3 Shared UI に置くための条件

コンポーネントを `shared/ui` に置くには、次のいずれかを満たさなければならない。

- 2 つ以上の feature が、同じ意味と同じ操作上の契約で安定して使用している。または
- プロジェクトで、アプリ全体の基本 UI primitive／デザインシステムのパターンとして明確に位置づけられている。

同時に、次を満たすべきである。

- feature 名がなくても、中立的な UI 名で説明できる。
- 利用側で、状態、アクセシビリティ、プラットフォームごとの差異、エラー時の動作に関する要件が一致する。
- 現在の JSX が似ているだけでなく、同じ理由で一緒に変更される見込みがある。
- `features/*`、ルート、API、認証、ストレージ、業務ストアに依存しない。
- 具体的な業務文言、ページの状態機械、利用側ごとの例外処理を含めない。
- 重要な操作について、アクセシビリティに対応し、テストから操作・検証するための手段を提供する。

次の状況だけでは、`shared` に置くべき根拠として不十分である。

- 2 か所のコードが、どちらも白い角丸カードを使っている。
- 2 つの Figma フレームが、現時点では同じ見た目になっている。
- コピーが 2 回発生しているが、今後の変更の方向性が異なる。
- `isProfilePage`、`isCompactHome`、`hideXxx` を増やし続けなければ共有できない。

Button、Text、Surface、IconButton など、明らかにプロジェクトのデザインシステムに属する primitive は、最初の利用側ができた時点で `shared` に置いてよい。ただし、デザインシステムの一部であることを、プロジェクト固有の規約で明確にしなければならない。

### 4.4 追加前に再利用を検討する

コンポーネント、Hook、ユーティリティ、Use Case を追加または書き直す前に、最低限、次の手順で再利用を検討しなければならない。

1. 意味を表す名前、ユーザーの意図、主要な JSX 構造、特徴的なスタイルを手がかりに、現在の feature を検索する。
2. `shared/ui`、`shared/hooks`、`shared/utils`、トークン、公開エントリーポイントを検索する。
3. 候補となる実装の props、状態、アクセシビリティ、プラットフォーム上の動作、それを直接使う箇所を確認する。ファイル名だけで判断しない。
4. 「そのまま再利用、拡張、より低い層の機能を抽出、独立した実装を維持」から 1 つを選び、理由を記録する。
5. 拡張後もすべての利用側にとって API が自然に使える場合にだけ、既存の共通コンポーネントを拡張する。

実装前の出力には、少なくとも次を列挙する。

```text
再利用候補：既存の Button、SettingsRow、useDisclosure
判断：Button を再利用。SettingsRow は意味が異なるため feature 内の実装を維持。
      2 つの業務コンポーネントを統合せず、共通の RowSurface primitive を抽出する。
```

候補が見つからなかった場合も、「検索済み。意味が一致する実装は見つからなかった」と明記すべきである。既存コードを検索せずに類似コンポーネントを追加してはならない。

### 4.5 重複コードの分類

重複コードを先に分類し、その後で抽象化の方法を決める。

| 重複の種類 | 優先する配置先 | 説明 |
| --- | --- | --- |
| 色、間隔、角丸、フォントなどのデザイン値 | トークン | 見た目の基準を一元化する。値の重複を解消するために業務コンポーネントを作らない。 |
| 見た目の構造も操作の意味も同じ | feature UI または shared UI | まず feature 内に置き、契約が安定してから共通層に移す。 |
| 動作は同じだが、見た目の構造が異なる | Headless Hook / Controller の補助機能 | 状態と動作を再利用し、UI まで同じにすることは強制しない。 |
| 同じ業務ルール、バリデーション、変換 | `model/` または純粋関数を置く `utils/` | React への依存や副作用を含めてはならない。 |
| 同じ多段階の業務処理 | `use-cases/` | ユーザーの意図と不変条件を再利用し、ページのフィードバック処理は再利用しない。 |
| サードパーティ、プラットフォーム、DTO の差異を扱う同じ処理 | Adapter | 外部との違いを吸収する。 |
| 現在の見た目だけが似ており、状態と今後の変更の方向性は異なる | 独立した実装を維持 | より低い層の primitive またはトークンを再利用してよい。 |

判断のポイントは「コードの見た目が同じか」ではなく、次の点にある。

> 要件が変わったとき、これらのコードは同じ理由で一緒に変更されるべきか？

判断がつかない場合は、まず feature 内に残す。抽出するのは、低い層にある、最小限で安定しており、共通化の妥当性が明らかな部分だけにする。

### 4.6 抽象化の階層と適度な共通化

次の順序で、安定して再利用できる最も低い抽象化の層を探す。

1. **トークン**：色、余白、角丸、文字組み、アニメーション。
2. **Primitive**：Text、Button、Surface、Divider、IconButton、Field の外枠。
3. **動作を担う機能**：純粋関数、セレクター、バリデーション、Headless Hook。
4. **Feature Pattern**：1 つの feature だけに使う Row、Card、Section、フォームブロック。
5. **Shared Pattern**：feature をまたいで使う、特定の業務に偏らず、契約が安定した複合パターン。
6. **Page / Flow**：原則として共通化せず、共有機能の組み立てだけを行う。

「2 回目に評価し、3 回目の安定した利用で通常は抽出する」という経験則を採用する。

- 1 回目：feature 内で完結する、わかりやすい実装を優先する。
- 2 回目：意味、変更理由、状態に関する契約を比較し、必要なら低い層の部分だけを抽出する。
- 3 回目も安定して使える場合：引き続き同じ理由で変わるなら、通常は共通部分を抽出し、既存の実装を移行すべきである。

回数だけで機械的に判断するルールではない。セキュリティ上の不変条件、プロジェクト共通の primitive、デザインシステムの一部と明確に定められたパターンは、より早く抽出してよい。2 つの利用側のコードが同じでも、今後の変更の方向性が異なるなら統合すべきではない。

### 4.7 共通コンポーネントへの移行と feature への切り戻し

feature から `shared` へ移す際は、次を行わなければならない。

- 既存の利用側と、追加が見込まれる利用側を明確にする。
- 最小限の props、デフォルトの動作、状態に関する契約、アクセシビリティ、プラットフォームごとの差異を定義する。
- 直接利用するすべての箇所を更新し、重複する旧実装を削除する。
- 安定したバリアントと重要な操作に対して、テストまたはコンポーネントの使用例を追加する。
- プロジェクトのコンポーネントカタログまたは `app-specific.md` に公開エントリーポイントを記録する。

次の兆候が見られる場合は、分割する、feature に戻す、より低い層の primitive を抽出し直すなどの対応をすべきである。

- Shared props にページ名、ルート、feature の列挙型、利用側ごとに専用の真偽値が複数含まれるようになる。
- 呼び出し元ページに応じて内部で条件分岐する。
- 利用側から、内部要素のスタイル、描画を上書きする指定、`mode="custom"` を大量に渡している。
- 1 つの利用側を変更するたびに、無関係な利用側に影響しないか心配になる。
- コンポーネント名は抽象的になる一方で、複数の責務がますます混在している。

共通化は、一度進めたら戻せないものではない。誤った抽象化は早めに分割し直すべきであり、「再利用率」を維持するために例外処理を増やし続けてはならない。

### 4.8 万能な設定より組み合わせを優先する

差異の種類に応じて API を選ぶ。

- 構造は同じで、見た目の違いが限られた選択肢に収まる場合：`variant`、`size`、`tone` などの有限の列挙型を使用する。
- 構造が実際に異なる場合：真偽値の props を増やし続けず、children、slot、小さなコンポーネントの組み合わせを使う。
- 動作は同じで、見た目が異なる場合：Headless Hook または純粋な状態モデルを再利用する。
- 見た目は同じで、業務状態が異なる場合：外部から状態とコールバックを受け取る、制御された表示コンポーネントを使う。
- 最上位のレイアウトで本当に必要な場合だけ、限定的に `style` を公開する。内部の各ノードのスタイルを任意に上書きできる仕組みは公開しない。

巨大な設定でヘッダー、フォーム、リスト、フッター、ルート、業務アクションをまとめて決めるなど、ページ設定を読み解いて何でも処理するコンポーネントを作ってはならない。設定駆動の設計は、フィールドの集合が明確で、意味が一致し、まとめてレンダリングする必要がある構造にだけ適している。

### 4.9 Props のルール

再利用可能なコンポーネントでは、次のように意味が伝わる props を優先する。

```ts
label
value
selected
disabled
loading
variant
size
tone
layout
onPress
onChange
onChangeText
onClose
```

ルール：

- コールバック名は `onXxx` に統一し、実装手順ではなくユーザーの意図を表す。
- 業務上の選択状態、入力値、スイッチの状態、フローのステップは、原則として外部から制御する。
- 安定した見た目の分岐には有限の列挙型を使い、`isPrimary`、`isLarge`、`isForXxxPage` などの真偽値を増やし続けない。
- 任意の prop には、省略時の動作を明確に定めなければならない。
- コンポーネントの動作に本当に欠かせない入力だけを必須にする。
- Shared コンポーネントは、必要最小限のスタイル拡張と、ネイティブのアクセシビリティに必要な設定項目だけを公開する。
- Shared props に feature 名、フローのステップ、バックエンド DTO、業務用の列挙型を含めない。
- 呼び出し側の数行を減らすために、ナビゲーション、API、Toast、状態機械をコンポーネントに詰め込まない。

### 4.10 1 コンポーネント 1 責務

- 各 UI ファイルでは、原則として外部に公開するコンポーネントを 1 つだけ定義する。
- 短く、状態を持たず、そのファイル内でしか使わない描画用の補助関数は残してよい。
- ページ、セクション、複雑なコントロールは責務に沿って分け、見た目の一部分を任意に切り出すような分割はしない。
- JSX やメソッドを別ファイルへそのまま移すだけでは、有効な分割とはならない。
- 分割後のモジュールは、意味、変更の単位、テストの単位のいずれかが明確でなければならない。

次の兆候は、通常、分割が必要なことを示す。

- 同じファイルにヘッダー、フォーム、プレビュー、状態表示、操作領域がすべて含まれている。
- 条件付きレンダリング、switch、プラットフォームごとの分岐が大量にある。
- 複雑な SVG、グラデーション、マスクが業務の構造と混在している。
- ハンドラー、エフェクト、JSX が入り交じっている。
- 1 つの変更理由が複数の無関係な領域に頻繁に影響する。

次の兆候は、さらに分割すべきではないことを示す。

- 新しいファイルには、別の関数を呼び出す処理が 1 つあるだけ。
- 1 つのアクションを追うために、1 行しかないファイルをいくつも行き来しなければならない。
- 分割しても理解しやすくならず、import と名前だけが増えている。

### 4.11 デザインパターンの選択条件

デザインパターンは、状態、変化する箇所、依存関係を明確にするために使う。層を増やすためには使わない。原則として、クラスの継承よりも、関数、組み合わせ、型を優先する。

| 状況 | 推奨パターン | 使用すべきでない場合 |
| --- | --- | --- |
| 少量の局所的な状態、1 回の同期操作 | 直接のハンドラー / 局所的な Hook | Use Case、Repository、Factory を作らない。 |
| 1 つのユーザーアクションに、バリデーション、複数の副作用、キャッシュまたは並行処理のルールが含まれる | Controller + Use Case | 業務ルールを伴わない API 呼び出しが 1 回あるだけ。 |
| 状態が互いに排他的、不正な組み合わせがある、遷移が直前の状態に依存する | Reducer / 明示的な状態機械 | 互いに影響しない 2 つの真偽値。 |
| 同じアルゴリズムをモード、権限、製品方針に応じて切り替える | Strategy | 安定した実装が 1 つだけ。 |
| iOS/Android、ネイティブモジュール、サードパーティ SDK、DTO との違いを切り離す | Adapter | 関数名を変えるだけ。 |
| 同じドメインのデータが API、キャッシュ、オフラインストレージにあり、扱い方を統一する必要がある | Repository | エンドポイントが 1 つで、キャッシュ／オフラインのルールがない。 |
| 同じ動作を異なる UI で使う必要がある | Headless Hook | UI も動作も異なる。 |

パターンを導入する前に、「どの条件分岐、ルールの重複、外部への依存、不正な状態、テストの難しさを解消するのか」に答えられなければならない。答えられない場合は、単純な実装のままにする。

### 4.12 明示的な制御フローと呼び出しチェーン

主要なユーザーアクションは、次の追跡可能な経路に従う。

```text
UI event
  -> Controller action
      -> 必要に応じて Use Case
          -> API / storage / cache adapter
      <- typed result
  -> Controller が UI state / ナビゲーション / フィードバックを更新
```

ルール：

- 主要なアクションごとに、`submitProfile`、`publishPost`、`retryLoad` など、処理全体を担う統括関数を 1 つだけ設ける。
- バリデーション、ロック、重複防止、呼び出し順序、エラーマッピング、成功後の状態処理は、責任範囲が明確な箇所で順を追って読めるようにすべきである。
- 関数は少なくとも、意味を伝える命名、入力変換、不変条件、分岐の判断、副作用の境界、エラーマッピング、キャンセル／ロック、差し替え可能な実装、必要な計測処理のいずれかの役割を担うべきである。
- 何の役割も加えず、同じ引数で次の関数を呼ぶだけのラッパーは削除すべきである。
- `handleSave -> submit -> executeSave -> service.save` のように、業務上の意味を持たず処理を渡すだけの層が 2 層以上続いてはならない。
- Controller のアクションから、同じページ内で直接呼び出せるフローを EventBus 経由で間接的に起動すべきではない。
- Use Case は型を持つ結果を返す。Toast、Dialog、ナビゲーションの判断は Controller が行う。
- 中核となるフローを、1 行だけの非公開メソッドに細切れにしない。重要な手順は、順を追って読める 1 つの統括関数にまとめる。

非推奨：

```ts
const handleSave = () => submit();
const submit = () => executeSave();
const executeSave = () => profileService.save(form);
```

単純なフローは直接表現する。

```ts
const save = async () => {
  if (state.status === 'submitting') return;

  const parsed = validateProfile(state.form);
  if (!parsed.ok) {
    dispatch({ type: 'validationFailed', errors: parsed.errors });
    return;
  }

  dispatch({ type: 'submitStarted' });
  const result = await profileApi.update(parsed.value);
  dispatch(mapUpdateResultToEvent(result));
};
```

複雑なフローは、名前を変えて呼び出すだけの層を追加せず、1 つの Use Case で業務処理の順序を表現する。

```ts
export async function updateProfile(
  input: UpdateProfileInput,
  deps: UpdateProfileDependencies,
): Promise<UpdateProfileResult> {
  const parsed = validateProfile(input);
  if (!parsed.ok) {
    return { type: 'validation-error', errors: parsed.errors };
  }

  const profile = await deps.profileRepository.update(parsed.value);
  await deps.profileCache.replace(profile);

  return { type: 'success', profile };
}
```

### 4.13 Hook と Controller のルール

Hook の内部は、次の順序で読めるように記述する。

1. Context、依存関係、外部 Hook
2. `useState` / `useReducer` / `useRef`
3. 派生値とセレクター
4. ページに公開するアクション
5. エフェクト
6. 戻り値

Hook は次のようにすべきである。

- 局所的な汎用の動作には `useSomething`、ページやフローの統括には `useSomethingController` を使用する。
- ページが本当に必要とする状態とアクションだけを公開する。`{ state, actions }` など、安定した読みやすい構造を推奨する。
- 公開するアクションは、処理全体を統括する唯一の箇所を直接呼び出す。同じ意味の別名ハンドラーを間に挟まない。
- React のライフサイクル、フォーカス、購読、リクエストのキャンセル、ナビゲーション結果の変換を担う。
- タイマー、購読、アニメーションをクリーンアップし、非同期処理の競合が残らないようにする。
- 純粋な計算、バリデーション、セレクター、状態遷移は `model/` または純粋関数を置く `utils/` に移す。
- 業務処理が React なしでテストでき、複数の手順にわたるルールを含む場合は `use-cases/` に移す。
- 互いに関連する真偽値を何十個も返さず、判別可能なユニオン型、Reducer、明確なビューモデルを使用する。

次のいずれかに該当する場合は、Controller、Use Case、Reducer の分割を検討すべきである。

- 1 つの Hook が、互いに独立した 2 つ以上のユーザーフローを同時に統括している。
- 複数の非同期処理について、実行順序、排他制御、リトライ、キャンセル、古いレスポンスの扱いに関するルールがある。
- 同じ業務ルールがエフェクト、ハンドラー、描画の分岐に重複している。
- 状態の組み合わせが、存在し得ない UI 状態を表せてしまう。
- React コンポーネントをマウントしなければ中核の業務ルールをテストできない。

### 4.14 Use Case のルール

Use Case は、1 つのユーザーの意図を実行するために、業務処理を統括する必要が実際にある場合だけ導入する。例：

- バリデーションの後に、1 つ以上の外部依存先を呼び出す
- 権限、セッション、冪等性、トランザクションの順序、キャッシュ整合性のルールが必要
- 同じ操作が複数の箇所から呼び出される
- 成功、失敗、並行処理の分岐を TypeScript だけでテストする必要がある

Use Case が必ず守る事項：

- `publishPost`、`deleteAccount` のように、動詞と業務上の対象を組み合わせて命名する。
- React、React Native UI、Expo Router、Toast、ページコンポーネントを import しない。
- 明確に定義した入力を受け取り、判別可能なユニオン型または明確な結果型を返す。
- 重要な業務処理とその順序を 1 か所で示す。
- 依存性注入は、実際に差し替える必要のある依存先、テストの分離、複数の実装への対応にだけ使う。関数ごとに空のインターフェースを作らない。
- 変化する箇所のない 1 行の API 呼び出しを、クラス、Factory、Repository で包まない。

### 4.15 Reducer と状態機械のルール

次の場合は、Reducer または明示的な状態機械を優先する。

- `idle`、`loading`、`success`、`error` などの状態が相互排他的である。
- 複数の真偽値を使うと、`loading` と `submitted` が同時に成立するなどの不正な組み合わせが生じる。
- 遷移が現在の状態に依存し、リトライ、キャンセル、楽観的更新、ロールバックがある。
- 同じイベントが状態によって異なる振る舞いをする。

ルール：

- 状態の表現には、TypeScript の判別可能なユニオン型を優先する。
- Reducer は純粋な状態遷移だけを行い、リクエスト、ナビゲーション、ストレージの読み書きを行わない。
- 副作用は Controller または Use Case が実行し、その結果イベントを Reducer に dispatch する。
- 「状態機械」の概念を使うからといって、サードパーティライブラリの追加を必須にしない。`useReducer` と明示的な状態遷移で十分なら、単純な実装のままにする。
- テストでは、許可される遷移、拒否される遷移、重要な不変条件を確認する。

### 4.16 リストと繰り返し構造

- カード、メニュー、選択肢、行項目を繰り返し表示する場合は、データに基づいてレンダリングする。
- データ駆動で置き換えるのは、実際に構造が同じ繰り返し部分だけとする。異なる業務上の意味を、大量の `type` 分岐を持つ万能レンダラーに詰め込んではならない。
- データ量、仮想化の必要性、入れ子構造に応じて `FlatList`、`SectionList`、単純な `map` を選ぶ。
- 同じ階層の項目では、高さ、内側の余白、区切り線、間隔を統一しなければならない。
- 先頭、末尾、選択済み項目の見た目の差異は明示的に表す。
- 将来ページ分割や動的な増減があり得るデータには、初版から安定したキーを用意し、リストの境界を明確にする。
- 配列のインデックス、表示文言、一時的な時刻値を長期的に安定した ID として使用しない。

### 4.17 スタイル、デザイントークン、Typography

スタイルの構成は読みやすさを基準とする。

- 小規模で、1 つのコンポーネント内でしか使わない非公開の `StyleSheet.create` は、不要なファイル間の移動を減らすため、同じファイルの末尾に置いてよい。
- スタイルが多い、見た目の領域が明確に分かれている、プラットフォームごとの分岐がある、複数ファイルで共有する、コンポーネント本体が読みにくくなる場合は、同じディレクトリの `ComponentName.styles.ts` に分ける。
- コード行数だけで機械的に分割してはならず、動的な業務ロジックをスタイルファイルに置いてもならない。
- プロジェクトでスタイリングの方式が定められている場合は、全体で同じ方式を使い、一部だけに別の方式を混在させてはならない。
- JSX には、実行時の状態に本当に依存する最小限の動的スタイルだけを残す。

トークンのルール：

- 現在のアプリで定義済みの色、フォント、間隔、角丸、影、アニメーションのトークンを優先する。
- 繰り返し使うデザイン値を、各所にリテラルで書いたままにしてはならない。
- 別のアプリが特定のトークンを使っているという理由で、現在のアプリにコピーしてはならない。
- Figma の値とコードのトークンが近いが完全には一致しない場合は、既存のトークンに結び付けるべきかを先に判断し、その後で差異を説明する。
- グローバルトークンの追加または変更はデザインシステムの変更に当たり、明示的な確認を必要とする。
- その箇所でしか使わない寸法は残してよいが、名前と用途を明確にしなければならない。

テキストでは、少なくとも次を確認する。

- `fontFamily`
- `fontSize`
- `fontWeight` または具体的なフォントマッピング
- `lineHeight`
- `letterSpacing`
- テキストの言語と、対応する字形がない場合のフォールバック

Figma Dev Mode のフォント名を機械的にコピーしてはならない。アプリが実際に読み込むフォントと、そのフォントが対象言語に対応しているかを確認する必要がある。

### 4.18 import、公開エントリーポイント、見つけやすさ

- プロジェクトに設定されたパスエイリアスを優先し、深い `../../` を避ける。
- 各ワークスペースで import してよい外部パッケージは、その `package.json` に宣言されたものだけとする。
- 利用側は、パッケージ内部の深いパスを使って公開 `exports` を迂回してはならない。
- feature の公開エントリーポイントからは、境界をまたいだ使用を明示的に認めたモジュールだけを export する。無制限の `export *` で内部実装をすべて公開しない。
- すべてのディレクトリにバレルファイルを作ることは避ける。バレルファイルが多すぎると、実際の依存関係が見えにくくなり、循環参照が増え、コード検索の結果も読みにくくなる。
- 型のみの import は、プロジェクトの TypeScript 規約に従い、不要な実行時コードが含まれないようにする。
- 共通コンポーネントには、意味が伝わり検索しやすい名前、公開エントリーポイント、最小限の使用例を用意すべきである。そのために、コンポーネントのドキュメント用サードパーティツールを新たな依存関係として追加する必要はない。

### 4.19 コードレビューで答えるべき質問

対象のページやフローをレビューする際は、次の質問にすぐ答えられるべきである。

1. この UI は既存の primitive / pattern を検索し、再利用しているか。別の類似コンポーネントと統合しなかったのはなぜか。
2. 共通化した実装の利用側で、意味、状態に関する契約、変更理由が一致しているか。
3. 現在の抽象化は万能コンポーネントにならず、安定して再利用できる最も低い層にあるか。
4. 状態はどこで管理され、どの状態が相互排他的か。
5. ユーザーアクションはどの UI コールバックから始まり、処理全体を担う統括関数はどこにあるか。
6. API、ストレージ、キャッシュ、ナビゲーションは、それぞれどの境界で発生するか。
7. 同じ引数を渡すだけのメソッドや、同じ意味のハンドラーをつないだ呼び出しチェーンはないか。
8. Reducer、Use Case、Strategy、Adapter、Repository を採用することで、どの具体的な問題を解決したか。
9. デザイン値の出典はどこか。両プラットフォームの違いはどこで扱っているか。
10. この共通コンポーネントの変更にあたり、直接利用するすべての箇所を確認したか。
