# 3. ルーティングとナビゲーションのルール

### 3.1 Router のエントリーポイント

- `mobile/app/` は、ルート宣言、レイアウト、最小限の橋渡しだけを担う。
- 実際のページ実装は `features/<feature>/pages/` に置く。
- ルートファイルは、原則として再エクスポートだけを行う。
- `app/_layout.tsx` はルートナビゲーション、Provider、グローバルなシステム設定だけを担当する。
- ルートファイルに Hook、静的データ、スタイルを大量に記述してはならない。
- ルートを表す文字列は、プロジェクトのルート定数または型安全なエントリーポイントで一元管理する。
- `router.push`、`replace`、`pathname`、`Stack.Screen name`、`Tabs.Screen name`、`initialRouteName` にハードコードを散在させてはならない。
- `index.tsx` の使用可否、ルートグループの固定名称、パスエイリアスの形式は、プロジェクト固有の規約で定める。

### 3.2 ルートグループ

ルートグループは、次のように、ナビゲーションの安定した区切りを表すために使用する。

- 起動フロー
- ログイン前のフロー
- ログイン後のフロー
- Modal フロー
- その他の安定した共通の外枠

ルール：

- グループはナビゲーションの区切りを表すものとし、一時的なページの分類には使わない。
- 同じフローのページは、できるだけ同じ Stack で管理する。
- ヘッダー、タブバー、モーダルの外枠は、適切なナビゲーション階層に配置することで自然に決まるようにする。
- ページのスタイルやナビゲーションコンテナの動的なアンマウントを使って、ルートの階層を見かけだけ再現してはならない。

### 3.3 Tabs と Stack

```text
Root Stack
└── App Route Group
    └── Tabs
        ├── Tab A Stack
        │   ├── Main
        │   └── Detail / Edit / Filter
        └── Tab B Stack
            └── Main
```

必ず守る事項：

- Tabs は第 1 階層の移動先を切り替える役割だけを担う。
- 同じ Tab の第 2、第 3 階層のページは、その Tab 自身の Stack で管理する。
- 下部のタブバーは、Tabs のレイアウトに 1 回だけ定義する。
- 複数のページでタブバーを重複して描画しない。
- 詳細ページ、編集ページ、設定の下位ページを、タブに見せかけて実装しない。
- `return null`、高さを 0 にする、画面外へ移動する、Tabs を条件付きでアンマウントするといった方法で、タブバーを隠さない。
- すべての Tabs を覆う全画面ページは、Tabs の外側の Stack に配置する。
- 特定の Tab に属するサブフローは、その Tab の Stack に留める。

### 3.4 ナビゲーション操作の使い分け

- 詳細、編集、次のステップへ進む場合：プロジェクトで定めた push 操作を使用する。
- 戻る場合：ネイティブの back 操作を優先し、戻るジェスチャーを維持する。
- replace は、フローの中で実際に履歴を置き換える必要がある箇所にだけ使用する。
- タブの切り替えはタブ本来の操作として実装し、Stack の push で代用してはならない。
- モーダルのフロー全体を閉じることと、モーダル内の前の階層に戻ることは別の操作である。誤ったナビゲーション操作を使って混同してはならない。
- 具体的な遷移アニメーション、ジェスチャーの有効／無効、所要時間は、プロジェクト固有のアニメーションルールで定める。同種のナビゲーションは一貫させなければならない。

### 3.5 ページの分類

ページを追加する前に、どの分類に属するかを決定しなければならない。

1. 特定の Tab のルートページ
2. 特定の Tab 内のサブフロー
3. Tab をまたぐ全画面ページ
4. ルートレベルのモーダルフロー
5. ページ内部の Sheet / Dialog

この分類により、ページを配置する Stack、タブバーの表示有無、閉じる操作の意味、戻る際の動作が決まる。

### 3.6 Modal の分類

ルートレベルの Modal が適する状況：

- 内部で複数のステップを移動する
- 独立した履歴とシステムの戻る操作が必要
- 現在の Tabs を覆う必要がある
- 閉じる操作でフロー全体を終了する

ページ内の Modal / Sheet が適する状況：

- 短い選択肢リスト
- 1 回の確認
- 日付またはフィルターの選択 UI
- 独立したルート履歴が不要な簡単な操作

### 3.7 ナビゲーションの受け入れ確認

成果物の引き渡し前に確認する事項：

- 正しい入口からページに到達できる。
- 戻り先が正しい。
- replace が誤った履歴を残さない。
- 画面遷移中にタブバーの位置が急に変わらず、表示が遅れず、重複して描画されない。
- Modal を閉じる操作の意味が正しい。
- iOS の戻るジェスチャーと Android のシステム戻る操作が使える。
- ナビゲーション階層の切り替えで、セーフエリアと StatusBar にちらつきや重なりによる表示の隠れが発生しない。
