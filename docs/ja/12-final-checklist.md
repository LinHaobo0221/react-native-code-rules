# 12. 最終チェックリスト

### ディレクトリとアーキテクチャ

- [ ] ページの実装を、該当する feature の `pages/` に配置した。
- [ ] Router ファイルは、エントリーポイント、レイアウト、再エクスポートのみを担当している。
- [ ] UI、Controller Hook、Use Case、Model、API、data、types、utils の責務が明確である。
- [ ] 単純な場面に、Controller、Use Case、Repository、クラスを無理に追加していない。
- [ ] `shared` は、実際に安定して再利用されているか、デザインシステムのプリミティブであることが明確であり、業務固有の意味を持たない。
- [ ] 依存関係の逆向きの参照、EventBus による迂回、暗黙的なグローバルの結合がない。
- [ ] ファイル名、公開エントリーポイント、スタイルの配置がルールに沿っている。

### 再利用と共通化

- [ ] コンポーネント、Hook、ユーティリティ、フローを追加する前に、既存実装を検索した。
- [ ] 再利用候補と、直接再利用する、拡張する、低い層の機能を抽出する、独立したままにするという判断の理由を記録した。
- [ ] 共通化の根拠は、意味、状態に関する契約、今後変更が生じる理由が同じことであり、見た目の類似やコピー回数だけではない。
- [ ] 抽象化は安定して共有できる最も低い層に置き、トークン、プリミティブ、振る舞い、純粋なルールの再利用を優先した。
- [ ] Shared の props に、ページ名、ルート、feature の列挙型、特定の利用側専用の真偽値、制限なくスタイルを変更できる仕組みがない。
- [ ] 共通化後に重複する旧実装を削除し、すべての直接の利用側を確認した。
- [ ] 適切でなかった抽象化は分割するか元の層に戻し、「再利用率」のために特別扱いを増やしていない。

### 制御フローとデザインパターン

- [ ] 主要なユーザー操作ごとに、UI のコールバックから、処理全体を統括する唯一の箇所まで追跡できる。
- [ ] 主要な手順、処理を打ち切る条件、呼び出し順序、エラーマッピング、成功時の処理を、明確な境界の中で順に読み取れる。
- [ ] `handle -> do -> execute -> service` のように、呼び出しを中継するだけの処理が連なっていない。
- [ ] 抽象化した各関数が、意味、変換、不変条件、境界、並行処理の制御、差し替え可能性のうち、少なくとも 1 つの価値を持っている。
- [ ] Use Case は React、UI、Toast、Router に依存せず、Reducer は副作用を実行していない。
- [ ] Reducer、状態マシン、Strategy、Adapter、Repository、クラスには、それぞれ導入を必要とする明確な複雑さがある。
- [ ] 型付きの結果、判別可能なユニオン型、状態の不変条件によって、隠れた分岐と不正な状態を防いでいる。

### Figma と見た目

- [ ] 起点となるノード、ノードツリー、Auto Layout、主要な子ノードを確認した。
- [ ] ノード ID、コードの配置先、アセットのエクスポート、確認を省略した理由を記録した。
- [ ] Figma のコンポーネントとバリアントは、まず既存のトークン、プリミティブ、パターンに対応付けた。
- [ ] Auto Layout を適切に Flexbox に対応付けた。
- [ ] Component、Variant、Variables、トークンの対応関係を明確にした。
- [ ] フォント、フォールバック、各言語のグリフを確認した。
- [ ] 画像と SVG には正式なローカルアセットを使用し、用途のわかる名前を付けた。
- [ ] システム UI を手動で描画していない。
- [ ] レイアウト、フォント、色、アセット、状態、セーフエリア、両プラットフォームでの表示と動作を確認した。

### インタラクションとプラットフォーム

- [ ] 各コントロールに、用途に合ったネイティブコンポーネントを使用している。
- [ ] 入力、押下、切り替え、無効状態、読み込み中、Modal の操作に、実際のフィードバックがある。
- [ ] キーボードが入力欄や主要な操作を隠さない。
- [ ] セーフエリア、StatusBar、システムナビゲーションバー、エッジツーエッジ表示を検証した。
- [ ] iOS と Android の戻る操作、ジェスチャー、権限、フォント、Modal、システムのピッカーを検討した。
- [ ] 主要なコントロールに、アクセシビリティのロール、ラベル、状態、テスト用の識別手段を設けた。

### 品質と引き渡し

- [ ] 未承認の依存パッケージを追加していない。
- [ ] トークン、業務ルール、業務データの正とする情報源の重複や、上限のないキャッシュがない。
- [ ] Shared UI、Use Case、Reducer、Controller について、リスクに応じたテストを完了した。
- [ ] リスクに見合った format、lint、typecheck、test、bundle、ネイティブ環境のチェックを実行した。
- [ ] 成功、失敗、キャンセル、読み込み中、データなし、古い結果、競合の各経路をテストした。
- [ ] 今回発生した問題と既存の問題を切り分けて説明した。
- [ ] 最終的な報告で、主要なファイル、再利用の判断、操作フロー、検証結果、残っている差異を説明した。

### セキュリティとプライバシー

- [ ] クライアントのバンドルに、秘密として保持すべき情報が含まれていない。
- [ ] トークンが React の公開状態、ルート、URL、ログ、分析データに含まれていない。
- [ ] 認証は唯一の情報源で管理され、Persist Before Publish、Local-First Logout、stale-result fencing を備えている。
- [ ] 本番環境では、管理下にある HTTPS オリジンを使用している。
- [ ] 外部 URL、ディープリンク、ファイル、ネットワークのレスポンスを、信頼できない入力として扱っている。
- [ ] 権限を必要なときに要求し、拒否された場合の代替動作を用意している。
- [ ] ログアウト、アカウント切り替え、データ削除について、明確なクリーンアップ方針がある。
- [ ] iOS / Android のリリースビルドで、セキュリティに関する受け入れ確認を完了した。

## 13. 要約

```text
Figma / 確認済みのプロジェクト情報
        ↓
app のルートエントリーポイント
        ↓
feature page
   ┌────┴────────────────────┐
   ↓                         ↓
feature ui              controller hook
   ↓                         ↓
shared ui primitive     optional use case
                             ↓
                     model / api / adapter
                             ↓
                    shared 基盤
        ↓
iOS / Android の両方でインタラクション、性能、セキュリティ、見た目の受け入れ確認を行う
```

共通規約は「コードをどう構成し、検証するか」を定め、プロジェクト固有規約は「現在のアプリで何を使うか」を定める。実装時は常に、**作る前に調べる、同じ理由で変更するものだけを抽出する、最も低い層で共通化する、1 つの操作の処理は 1 か所で統括する、単なる中継処理を作らない、パターンは実際の複雑さを解決するためだけに使う**という原則を守る。
