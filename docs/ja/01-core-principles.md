# 1. ルールの位置づけと使用範囲

### 1.1 共通規約で定めること

共通規約では、複数のアプリに共通する次の開発基準を定める。

- `mobile/` の標準ディレクトリ構造
- Page、UI、Hook、Data、API、Shared の責任範囲
- Expo Router のルート構成
- Figma ノードの読み取り、デザイン分析、アセットのエクスポート、見た目の受け入れ確認の手順
- iOS / Android 両プラットフォームでの操作、キーボード、Modal、セーフエリア、アクセシビリティ
- パフォーマンスの診断、レンダリングの境界、リスト、画像、リソースのライフサイクル
- 層ごとのテスト、非同期処理の競合テスト、ネイティブ環境での受け入れ確認
- 安全なストレージ、認証、ネットワーク、権限、プライバシーの最低品質基準
- 依存関係、チェック、変更範囲、成果物の引き渡し手順

### 1.2 利用側プロジェクトで定めること

各アプリのプロジェクトで、次を定義しなければならない。

- 色、フォント、間隔、角丸、影などのデザイントークン
- アニメーションの所要時間、イージング、画面遷移のパラメータ
- ブランドコンポーネント、画像、SVG、フォントアセット
- ルートグループ、ルートパス、タブ名、具体的なページパス
- API 契約、認証、ローカルストレージ、業務状態の管理方針
- Expo / React Native のバージョンと使用を許可するサードパーティの依存パッケージ
- 対象デバイス、具体的な性能上の許容上限、プロファイリングツール
- テストランナー、コンポーネントテスト／E2E テストのツール、CI の合格基準
- データ分類、権限、サードパーティ SDK、セキュリティリスクのレベル
- プロジェクト独自の Figma Library、デザインファイル、ページリンク

### 1.3 ルールの優先順位

競合が発生した場合の優先順位は次のとおりとする。

1. ユーザーが現在明示している要件と制約
2. 利用側リポジトリの、より具体的な `AGENTS.md` と `app-specific.md`
3. 本共通規約
4. 未規定の状況での保守的なエンジニアリング判断

プロジェクトのルールでは、デザインの値、依存関係の選択、プロジェクトごとの拡張が明示的に認められた事項を上書きしてよい。ただし、アクセシビリティ、両プラットフォームとの互換性、型安全性、保守性の最低基準を、説明なしに引き下げてはならない。例外が必要な場合は、理由、影響範囲、代替策、受け入れ確認項目を記録しなければならない。

### 1.4 言語の指定と必読文書

利用側リポジトリでは、見つけられる場所にある `AGENTS.md` に次を宣言しなければならない。

```md
rules_language: ja
```

デバイスのロケール、コードの記述、個々のユーザーメッセージからルールの言語を推測してはならない。

React Native / Expo コードを生成または変更する前に、次を読まなければならない。

1. 現在のタスクの明示的な要件と制約
2. 利用側のルートおよび `mobile/` 配下の `AGENTS.md`
3. [00-core-rules.md](00-core-rules.md)。毎回全文を読む
4. 開発規約の分冊のうち、ルートの `AGENTS.md` が必読、またはタスクに応じて読むよう指定した節
5. プロジェクト固有の `mobile/docs/agents/app-specific.md` または同等の文書（存在する場合）
6. 今回のタスクに直接関係するディレクトリ、`package.json`、設定、既存コンポーネント、公開エントリーポイント、テスト
7. デザインが関係する場合は、Figma ノード、スクリーンショット、Variables、アセット

既存コードを読む際は、対象ファイルだけを見てはならない。UI、Hook、ユーティリティ、業務フローを追加する前に、次も確認しなければならない。

- 現在の feature にある関連実装
- `shared/ui`、`shared/hooks`、`shared/utils`、公開 API
- 既存のデザイントークン、基本コンポーネント、同じユーザーの意図を表す実装
- 対象コンポーネントまたはフローを直接利用するすべての箇所

本共通規約と、より具体的なプロジェクト固有のルールが一致しない場合は、開発品質の最低基準を下げていないことを条件に、プロジェクトのルールを優先し、成果物の引き渡し時に例外を記録する。タスクが Figma に一切関係しない場合は、Figma ノードを読む手順を省略してよい。ただし、コンポーネントの責務、再利用の検討、制御フロー、両プラットフォームの品質、セキュリティのルールは引き続き適用される。

### 1.5 タスク範囲と保守的な実装

デザイン再現タスク：

- 見た目の判断は、Figma とプロジェクトのトークンを基準にする。
- タスクで要求されたページ、状態、インタラクションだけを実装する。
- 静的ページやプロトタイプを、実際の API、認証、永続化の仕組みに独断で接続してはならない。

機能実装タスク：

- データソース、状態の所有者、エラー処理、ナビゲーション境界を先に明確にする。
- 業務状態を表示コンポーネントに詰め込まない。
- 確認が取れていない API 契約、データベース、保存方式を追加しない。

修正またはリファクタリングのタスク：

- 根本原因と影響範囲を先に確認する。
- 無関係な動作は変更せず、機能全体をついでに書き直さない。
- 同じフロー、共有の外枠、共通コンポーネントに影響する場合は、それらを直接利用する箇所をすべて確認する。

診断またはレビューのタスク：

- 原則として読み取り、検証、結論の説明だけを行う。
- 変更を明示的に求められていない場合は、修正を実装せず、新しいアーキテクチャを作らない。

情報が不足している場合：

- まずプロジェクトの既存実装とプロジェクト固有の文書を調べる。
- すでに安定して使われているパターンを再利用する。
- 最小限で、元に戻せる実装を採用する。
- 依存関係を追加せず、業務上の動作、トークン、アニメーションの仕組みを独断で作らない。
- 成果物の引き渡し時に、置いた仮定と規約からの差異を説明する。

選択肢によって製品の動作、データ構造、依存関係、プロジェクトの範囲が大きく変わる場合は、先に確認を求めるべきである。

### 1.6 弱めてはならない 6 つの厳守ルール

1. **作る前に調べる**：コンポーネント、Hook、ユーティリティ、フローを追加する前に、既存実装を検索し、再利用の判断を記録する。
2. **同じ理由で変わる場合だけ抽出する**：意味、状態に関する契約、将来の変更理由が一致するコードだけを共通化すべきである。見た目が似ていること自体を共通化の根拠にしない。
3. **安定して再利用できる最も低い層を選ぶ**：トークン、primitive、動作を扱う Hook、純粋なルールを優先して再利用し、すべてのページに対応する万能コンポーネントをいきなり作らない。
4. **Feature First**：妥当性が定まっていない抽象化はまず feature 内に留める。契約が安定し、複数の feature で使われ、特定の業務に偏らなくなってから `shared` に移す。
5. **1 つのアクションに 1 つの統括箇所**：主要なユーザーアクションごとに、処理全体を統括する唯一の箇所を設ける。重要な手順は、そこで順を追って読めるようにすべきである。
6. **処理を渡すだけの関数を禁止する**：意味、境界、変換、検証、エラーマッピング、並行制御、実装の差し替えやすさのいずれも加えないラッパー関数は削除すべきである。デザインパターンは、実際の複雑さを解消する場合だけ使用する。
