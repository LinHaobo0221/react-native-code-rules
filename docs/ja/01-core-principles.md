# 01 基本原則

> 本文書は、共通規約の目的、適用範囲、事実源、タスク境界、既定の判断方法を定義します。

## 目的

React Native / Expo App 間で一貫したエンジニアリング構造とコード品質を保ちながら、各 App が独自の Figma、ブランド、Token、モーション、業務要件に基づいて、まったく異なる見た目と機能を実装できるようにします。

生成または変更するコードは、次の条件を満たさなければなりません。

- 独立した Demo や接続できない断片ではなく、現在のプロジェクトへ直接組み込める
- 現在のプロジェクトのディレクトリ、命名、依存関係、技術選定に従う
- コンポーネントの責務が明確で、読み取り、テスト、レビュー、今後の変更が容易である
- 原則として iOS と Android の両方に対応し、Web の挙動をネイティブ受け入れ確認の代わりにしない
- Figma タスクでは設計を忠実に再現し、独自に見た目を統一または再設計しない
- タスク範囲外の業務ロジック、依存関係、永続化、インフラストラクチャを拡張しない

## 適用範囲

本規約は次の作業に適用します。

- React Native / Expo の画面およびコンポーネント開発
- Expo Router のルート構成
- Figma デザインの実装
- ローカル UI インタラクション
- 既存画面のリファクタリングと共通化
- モバイル API 接続、状態、データ表示のコード境界
- iOS / Android のプラットフォーム差異

本規約は次の内容を定義しません。

- 具体的な UI の外観
- Token の値
- ブランドカラーとフォント
- モーション時間と easing
- 業務フロー、API contract、データベース schema
- 固定されたサードパーティライブラリ一覧

これらは、利用側プロジェクトの `app-specific.md`、既存コード、Figma、またはタスク要件で定義しなければなりません。

## タスク開始前に確認する事実源

コード生成前に、次の順序で事実を確認します。

1. 現在のタスクで明示された要件と制約
2. 利用側リポジトリのルートおよび `mobile/` 配下の `AGENTS.md`
3. 本共通規約の全ファイル
4. 利用側プロジェクトの `app-specific.md`
5. 現在のプロジェクト構成、`package.json`、設定、既存コンポーネント、テスト
6. デザインが対象なら、Figma ノード、スクリーンショット、variables、アセット

過去の回答、キャッシュされた要約、別 App の実装だけを根拠に、現在のプロジェクトの事実を推測してはいけません。

## 共通規約とプロジェクト固有規約の境界

共通規約は「どのように構成し実装するか」を、プロジェクト固有規約は「現在の App が具体的に何を使うか」を定義します。例：

- 共通規約は繰り返す色を Token 化するよう要求し、プロジェクト規約は Token 名と値を決定します。
- 共通規約は画面遷移の意味を統一するよう要求し、プロジェクト規約はアニメーション種別、時間、easing を決定します。
- 共通規約は route 定数の集中管理を要求し、プロジェクト規約は route group と path を決定します。
- 共通規約は正しいフォント対応を要求し、プロジェクト規約は読み込むフォントと言語 fallback を決定します。

プロジェクト固有規約と共通規約が競合する場合：

- プロジェクト規約は、デザイン値、依存関係の選択、明示された構成拡張点を上書きできます。
- プロジェクト規約は、アクセシビリティ、両 OS 対応、型安全性、保守性の最低基準を説明なく下げてはいけません。
- 承認された例外には、理由、影響範囲、代替策、受け入れ条件を記録します。

## タスク種別の判断

変更前にタスク種別を判断します。

### デザイン実装

- Figma とプロジェクトの Design Token を視覚的な事実源とします。
- 要求された画面、状態、インタラクションだけを実装します。
- ユーザーが静的画面またはプロトタイプだけを求めている場合、実 API、Auth、永続化を独自に追加しません。

### 機能実装

- データソース、状態 owner、エラー処理、ナビゲーション境界を明確にします。
- 業務状態を表示コンポーネントへ入れません。
- 確認なしに API contract、データベース、ローカルストレージ方針を追加しません。

### 修正またはリファクタリング

- 先に根本原因と影響範囲を特定します。
- 無関係な挙動を維持し、局所的な要求を理由に機能全体を書き換えません。
- 問題が同一 flow、共有 shell、共通コンポーネントに属する場合、直接影響するすべての画面を確認します。

### 診断またはレビュー

- 原則として、読み取り、検証、結論の説明だけを行います。
- 変更が明示されていなければ、修正の実装や新しいアーキテクチャの作成は行いません。

## 保守的な実装

規約、デザイン、要件が不完全な場合：

- 現在のプロジェクト実装と固有ドキュメントを確認する
- 安定している既存パターンを再利用する
- 最小かつ可逆な実装を選ぶ
- 依存関係を追加しない
- 未確認の業務挙動を作らない
- デリバリー時に仮定と差異を説明する

選択によって製品挙動、データ構造、依存関係、プロジェクト境界が大きく変わる場合は、先に確認を求めます。

## 保守性

- 「動作する」だけを完了条件にしません。
- Page は組み立て、UI コンポーネントは表示、Hook は状態と挙動の編成を担当します。
- 重複実装は共通化を検討しますが、最小で適切な境界に抽出します。
- まだ存在しない仮想要件のために過度に抽象化しません。
- タスク範囲内で、不要に複雑なファイル、分岐、重複スタイルを整理します。
- ユーザーや他の開発者による無関係な変更を保持します。

## 同一 flow 全体の一貫性

問題が次のような flow または共有 shell に影響する場合：

- safe area と StatusBar
- Stack / Tabs 階層
- 共通 header と閉じる操作の意味
- 下部アクション領域
- キーボード回避
- Modal / Sheet モーション
- リストの loading / empty / error 状態

その構造を直接再利用するすべての画面を確認します。一部だけを変更する場合は、デリバリー時に対象範囲と未対象範囲を説明します。

## ドキュメントとコードの言語

- 説明言語は利用側プロジェクトの規約に従い、未指定なら現在のユーザーの言語に合わせます。
- package 名、route、コンポーネント、Hook、型、フィールド、エラーコードは元のコード表記を維持します。
- コメントは自明でない設計意図、プラットフォーム差異、制約を説明し、コードの表面的な動作を繰り返しません。
