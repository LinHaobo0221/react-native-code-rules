# 9. テストのルール

本節では、テスト戦略に関するルールを網羅する。

### 9.1 テストの目的

テストの目的は、変更、共通化、リファクタリング、アップグレードを行った後や異常な条件でも、ユーザーから見た動作、公開契約、システムの不変条件が保たれることを確認することにある。カバレッジの数値を上げることや、プライベートメソッドが呼ばれたことを確認するだけではない。

優先して守る対象：

- 主要なユーザーの操作経路と、その処理全体を統括するフロー
- 共通コンポーネントの公開 props、バリアント、アクセシビリティ、すべての直接の利用側
- データ変換、バリデーション、Use Case、業務上の計算
- Reducer の状態遷移と不正な状態の防止
- ナビゲーションと状態の境界
- API の契約とエラーマッピング
- 並行処理、キャンセル、古いレスポンスの扱い
- 認証、ストレージ、アカウントの切り替え
- 主要なインタラクションとアクセシビリティ
- 修正済みのバグの根本原因
- iOS / Android のネイティブ環境の差異

### 9.2 テストの階層

1. **静的解析**：フォーマッター、lint、TypeScript の型チェック、Expo config、アセット、バンドル、依存関係の境界、循環参照のチェック。
2. **純粋な Model / Use Case のテスト**：フォーマッター、パーサー、バリデーション、セレクター、Reducer、Strategy、Use Case、並べ替え、ページネーション結果のマージ、日付と数値の変換、エラーマッピング、ルートのマッピング。
3. **Hook / Controller のテスト**：入力、導出される View Model、読み込み、成功、エラー、リトライ、更新、追加読み込み、デバウンス、タイマー、クリーンアップ、購読、競合、楽観的更新、Use Case の結果から UI とナビゲーションへのマッピング。
4. **コンポーネントの操作テスト**：ユーザーの操作を通じて、文言、入力、押下、オン／オフの切り替え、選択、読み込み中、無効、エラー、データなし、選択済み、バリアント、アクセシビリティを検証する。
5. **結合テスト**：Page、Controller、Use Case、API Adapter、Provider、ルートガード、認証コーディネーター、ストレージの Adapter、キャッシュ、イベント、ページネーションが、実際に連携して動作することを検証する。
6. **ネイティブ／E2E テスト**：ネイティブのナビゲーション、戻るジェスチャー、キーボード、自動入力、セーフエリア、権限、ファイル、共有、ディープリンク、フォアグラウンドとバックグラウンド、EAS／リリースビルド、ネイティブアニメーションを検証する。

共通規約では、特定のテストランナーを必須としない。React Test Renderer は React Native 公式で非推奨とされている。新規プロジェクトでは、サポートが継続されており、ユーザーの操作を中心に検証するコンポーネントテストの仕組みを使用すべきである。既存プロジェクトでは保守を続けてよいが、移行計画と、ネイティブ環境での受け入れ確認で補う必要がある項目を記録する。

### 9.3 テストファイルの構成

- テストは、原則として対象モジュールの隣に置き、`name.test.ts` または `name.test.tsx` と命名する。
- 共通コンポーネントのテストでは公開契約を検証し、利用側固有の業務上の動作は各 feature のテストで扱う。
- Use Case と Reducer のテストでは、React コンポーネントをマウントする必要はない。
- feature をまたいで使うヘルパーは `mobile/test/` に置き、各 feature にコピーしない。
- フィクスチャを生成するビルダーや非同期処理を制御する deferred ヘルパーには、用途がわかる名前を付ける。
- テスト ID には、安定したドメイン別のプレフィックスを付けてもよい。要件、不具合、セキュリティレビューとの対応を追跡しやすくする。
- テストの説明では、Given / When / Then または Arrange / Act / Assert を明確にする。
- 1 つのテストでは、主に 1 つの動作か不変条件を確認する。
- 内部ファイルの分割方法、プライベートヘルパーの数、単なる中継呼び出しをテストで固定しない。

### 9.4 共通化と制御フローのテスト

共通化やフローのリファクタリングを行う場合は、少なくとも次を検証する。

- 新しい共通コンポーネントが、移行対象のすべての利用側で元の動作を維持している。
- バリアント、スロット、デフォルトの props によって、ある利用側の状態が別の利用側に漏れない。
- feature 内のコンポーネントを `shared` に移した後、ルート、API、認証、feature のストアに依存していない。
- 重複していた業務ルールを削除した後、正とする定義が 1 つだけ残っている。
- Controller が、公開アクションごとに処理を統括する Use Case または直接実装したフローを、1 回だけ実行する。
- Use Case の主要な処理の順序、失敗時の打ち切り、冪等性とロック、型付きの結果が正しい。
- Reducer が不正な状態の組み合わせを生まず、内部で副作用を実行していない。
- Adapter / Strategy の複数の実装が、同じ契約を満たしている。

`handleSave` が `submit` を呼び、さらに `submit` が `executeSave` を呼ぶことを検証しない。検証すべきなのは、ユーザーが送信した後の結果、外部への副作用の回数、状態遷移、エラーのフィードバックである。

### 9.5 結果が安定して再現できるテスト

テストはそれぞれ独立しており、繰り返し実行して同じ結果が得られなければならない。実行順序に依存させず、次の要素を制御する。

- 現在時刻とタイムゾーン
- タイマー、アニメーションフレーム、アイドルコールバック
- UUID と乱数
- ネットワークのレスポンス
- AppState
- プラットフォーム
- 権限
- ファイルのメタデータ
- ストレージの状態
- グローバルなシングルトンとモジュールキャッシュ

実時間の `sleep` や長いタイムアウトで、非同期処理の状態を待ってはならない。時間はフェイクタイマーか注入可能なクロックで制御する。非同期処理の順序は、deferred Promise か、動作を制御できるモックで管理する。

### 9.6 非同期処理と競合

推奨する型：

```ts
type Deferred<T> = {
  promise: Promise<T>;
  resolve: (value: T) => void;
  reject: (error: unknown) => void;
};
```

少なくとも次のケースを検証する。

- リクエスト A を先に送り、後から送ったリクエスト B の結果が先に返り、その後で A の結果が返る
- リクエストの完了前にページをアンマウントする
- フィルター、ルートパラメータ、アカウントを変更した後に、古いレスポンスが返る
- 更新と追加読み込みが同時に実行される
- データ更新の操作を素早く繰り返しタップする
- ストレージへの書き込みが完了する前にログアウトする
- 更新処理が完了する前にアカウントを切り替える
- リスナーのクリーンアップ後に、古いイベントが届く
- ピッカーや権限要求のフローから戻った時点で、AppState がまだ安定していない

テストでは、次の点も併せて検証する。

- どの結果を反映してよいか
- どの結果をキャンセルまたは破棄しなければならないか
- 読み込みロックが最終的に解除されるか
- キャッシュ、ストレージ、公開された状態、ユーザー向けのエラーが整合しているか
- 同じユーザー操作が、中継関数、effect、リスナーによって重複実行されていないか

実際のネットワーク遅延を使って競合を発生させてはならない。

### 9.7 モック、API、ナビゲーション、アクセシビリティ

- 純粋なモジュールの実装はできるだけそのまま使い、小さなフェイクを優先する。
- Network、Secure Storage、FileSystem、Image Picker、Linking、ネイティブモジュールは、明示的な Adapter を介してモック化する。
- モックの戻り値は、失敗、キャンセル、不正なレスポンスも含め、実際の契約に合わせる。
- 各テストで、呼び出し履歴、差し替えた実装、モジュール単位の状態をリセットする。
- モック、タイマー、マウント済みのルート、リスナーを次のテストに残さない。
- テスト対象である中核の動作そのものをモック化しない。
- Use Case の依存先には、必要最小限のフェイクを使用する。テストのために本番の業務ロジック一式を複製しない。
- API テストでは、メソッド、パス、クエリ、ボディ、ヘッダー、成功レスポンスの外側の構造、実行時の検証、エラー、タイムアウト、ネットワーク、`4xx`、`5xx`、ページネーション、キャンセル、古いレスポンス、リトライ、機密情報を含むヘッダーを検証する。
- 単体テストを、実際の本番エンドポイントに接続しない。
- ナビゲーションのテストでは、入口、パラメータ、push、replace、back、Modal 内で戻る操作、フロー全体を閉じる操作、Tab、ルートガード、ログアウト、ディープリンクを検証する。
- コンポーネントテストでは、ロール、ラベル、選択済み・チェック済み・無効・展開済みの状態、タップ対象の範囲、読み込み中の重複操作防止、エラーテキストとの対応関係を検証する。

### 9.8 スナップショット、バグ、カバレッジ、CI

- スナップショットは、小さく安定しており、レビューする価値が明確な出力にのみ使用する。
- 複雑なページや汎用の設定駆動レンダラーに対して、巨大なスナップショットを作らない。
- スナップショットの更新は、必ず人がレビューする。
- 業務上の計算、インタラクション、状態遷移、セキュリティの不変条件には、明示的なアサーションを使用する。
- バグ修正では、失敗するテストの作成、最小限の修正、回帰の検証、同じフローと共通コンポーネントの利用側の確認、ネイティブ環境での受け入れ確認を優先して行う。
- カバレッジは、検証の漏れを見つけるための手掛かりであり、それ自体が品質目標ではない。
- 認証、決済、権限、データ削除、Use Case の分岐、競合では、不変条件と分岐を基準にテスト範囲を決める。
- 重要な分岐をテストできていない場合は、自動化できない理由と、手動で受け入れ確認を行う方法を説明する。

推奨する CI の実行順序：

1. format / lint / typecheck / 依存関係の境界チェック
2. 高速な Model / Use Case の単体テスト
3. Hook / コンポーネント / 結合テスト
4. build / bundle / Expo config のチェック
5. 主要な E2E テストとリリースビルドのスモークテスト
