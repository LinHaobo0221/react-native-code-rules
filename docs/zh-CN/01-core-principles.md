# 1. 规则定位和使用边界

### 1.1 共通规约负责什么

共通规约统一以下跨 App 的工程标准：

- `mobile/` 标准目录结构
- Page、UI、Hook、Data、API、Shared 的职责边界
- Expo Router 路由组织
- Figma 节点读取、设计分析、资源导出和视觉验收流程
- iOS / Android 双端交互、键盘、Modal、safe area 和可访问性
- 性能诊断、渲染边界、列表、图片和资源生命周期
- 分层测试、异步竞态测试和原生验收
- 安全存储、Auth、网络、权限和隐私质量下限
- 依赖、检查、变更范围和交付流程

### 1.2 使用方项目负责什么

每个 App 必须自行定义：

- 颜色、字体、间距、圆角、阴影等 Design Token
- 动效时长、easing 和转场参数
- 品牌组件、图片、SVG 和字体资源
- route group、route path、tab 名称和具体页面路径
- API contract、Auth、本地存储和业务状态策略
- Expo / React Native 版本和允许的第三方依赖
- 目标设备、具体性能预算和 profiling 工具
- test runner、Component / E2E 工具和 CI 门槛
- 数据分类、权限、第三方 SDK 和安全风险等级
- 项目自己的 Figma Library、设计文件和页面链接

### 1.3 规则优先级

发生冲突时，优先级为：

1. 用户当前明确提出的需求和限制
2. 使用方仓库更具体的 `AGENTS.md` 和 `app-specific.md`
3. 本共通规约
4. 未覆盖场景下的保守工程判断

项目规则可以覆盖设计值、依赖选择和明确的项目扩展点，但不能无说明地降低可访问性、双端兼容、类型安全和可维护性下限。需要例外时，必须记录原因、影响范围、替代方案和验收点。

### 1.4 语言和读取要求

使用方仓库必须在可发现的 `AGENTS.md` 中声明：

```md
rules_language: zh-CN
```

不能根据设备 locale、代码文本或单条用户消息猜测规则语言。

生成或修改 React Native / Expo 代码前，必须读取：

1. 当前任务的明确需求与限制
2. 使用方根目录和 `mobile/` 下的 `AGENTS.md`
3. [00-core-rules.md](00-core-rules.md)，每次完整读取
4. 完整工程标准分册中由根目录 `AGENTS.md` 指定的必读章节和任务相关章节
5. 项目级 `mobile/docs/agents/app-specific.md` 或等价文档（如存在）
6. 与本次任务直接相关的目录、`package.json`、配置、已有组件、公共出口和测试
7. 涉及设计时的 Figma 节点、截图、Variables 和资源

读取现有代码时，不能只查看目标文件。新增 UI、Hook、工具或业务流程前，必须同时检查：

- 当前 feature 的相邻实现
- `shared/ui`、`shared/hooks`、`shared/utils` 和公开 API
- 已存在的 Design Token、基础组件和相同用户意图的实现
- 目标组件或流程的所有直接使用方

如果本共通规约与更具体的项目级规则不一致，以更具体且未降低工程质量底线的项目规则为准，并在交付中记录例外。任务完全不涉及 Figma 时，可以不执行 Figma 节点读取步骤，但组件职责、复用审查、控制流、双端质量和安全规则仍然有效。

### 1.5 任务范围和保守实现

设计还原任务：


- 以 Figma 和项目 Token 为视觉事实源。
- 只实现任务要求的页面、状态和交互。
- 静态页面或原型不能擅自接入真实 API、Auth 或持久化。

功能实现任务：


- 先明确数据来源、状态归属、错误处理和导航边界。
- 不把业务状态塞进展示组件。
- 未确认时不新增 API contract、数据库或存储方案。

修复或重构任务：


- 先确认根因和受影响范围。
- 保留无关行为，不借机重写整个功能。
- 同一 flow、共享壳层或共通组件受影响时，要检查所有直接使用方。

诊断或评审任务：


- 默认只读取、验证和说明结论。
- 未明确要求修改时，不实施修复或创建新架构。

信息不完整时：


- 先查项目现有实现和项目级文档。
- 复用已稳定存在的模式。
- 采用最小且可逆的实现。
- 不新增依赖、不创造业务行为、不自行发明 Token 或动效系统。
- 交付时说明假设和偏差。

如果不同选择会显著改变产品行为、数据结构、依赖或项目边界，应先请求确认。

### 1.6 六条不可被稀释的硬规则

1. **先查再建**：新增组件、Hook、工具或流程前，先搜索已有实现并记录复用判断。
2. **同因才抽**：只有语义、状态契约和未来变化原因一致的代码才应共通；视觉相似本身不是共通依据。
3. **最低稳定层复用**：优先复用 Token、primitive、行为 Hook 或纯规则，不直接制造覆盖所有页面的万能组件。
4. **Feature First**：不确定的抽象先留在 feature；合同稳定、跨 feature 且无业务偏向后再提升到 `shared`。
5. **一条动作一处编排**：一个主要用户动作只能有一个权威流程编排点，关键步骤应在该处按顺序可读。
6. **禁止空转转发**：不增加语义、边界、转换、校验、错误映射、并发控制或可替换性的包装函数应删除；设计模式只在解决真实复杂度时使用。
